# Plan 141 — accept a replaced Copilot executable on Linux (issue #397)

Owner: pij-minor-unicorn (prime). Source: GitHub issue #397 (Jordan, 2026-09-08): "Linux: native Copilot extension reload fails after an in-place CLI upgrade". Jordan 2026-09-09: "next there is an issue on copilot issues".

## Problem (verified in source 2026-09-09 on main 7e9bf2b1)
After the installed Copilot binary is upgraded in place while a Copilot host keeps running, the kernel reports that host's executable as `/…/copilot (deleted)`. Three identity checks then refuse a host that is genuinely alive, and the banner lies about what happens next:
1. `.copilot/extensions/pij/extension.mjs:36` — Linux `inspectProcess` returns `readlink(/proc/<pid>/exe)` verbatim, suffix included.
2. `.copilot/extensions/pij/store.mjs:1029` — `resolveNativeHost` matches `/(?:^|[/\\])copilot(?:\.exe)?$/` against that string; the suffix fails it → "Cannot verify a Copilot host ancestor in the exact pane".
3. `crates/daemon/src/registration.rs:1113` — `is_copilot_host` takes `file_name()` of the observed executable; `copilot (deleted)` hits `_ => false`. `read_native_process` (Linux cfg, :1141) is where the link is read.
4. `store.mjs` `createNativeReporter` gives the outer, terminal `extension-unavailable` event (extension.mjs:160 — after `if (!error.retryable) throw error;` at :150) the same advice as the retry loop: "retrying when available". Nothing retries. Loader readiness (`extensions_reload` says ready) is not registration readiness.

## Acceptance
- AC1 Normalize the kernel executable link at observation, once per side. A trailing ` (deleted)` suffix (kernel convention for an unlinked/replaced exe) is stripped from the path BEFORE any basename match: Rust `read_native_process` (Linux cfg) via one named fn (e.g. `normalize_kernel_exe(&str) -> (String, bool)`), and the extension's Linux `inspectProcess` via one exported helper in `store.mjs` used by extension.mjs. The observation keeps the fact: `NativeProcess.executable_replaced: bool` and the extension's observed object `replaced: true|false`. No other matcher changes; argv/entrypoint, ancestry, pane, proc_start, incarnation and native-session checks are untouched.
- AC2 Daemon accepts the replaced host: a Linux-only (`#[cfg(target_os = "linux")]`) test copies `/bin/sh` to a tempdir as `copilot`, spawns it with `arg0("copilot")` + `-c 'echo ready; read line'` (wait for `ready` — see `real_shell_process_is_not_an_actual_copilot_host` for why), unlinks the copy, then `read_native_process(pid)` → `is_copilot_host()` is true AND `executable_replaced` is true. Negatives in the same test: the same recipe with the file named `copilot-evil` → false; a `/proc` link of `/x/copilot (deleted)` with argv0 `sh` → false (forged argv0 still loses). This test is the RED witness: run it on the pre-fix tree first and capture the failure.
- AC3 Extension accepts the replaced host: `identity.test.mjs` cases where the host ancestor's `command` is `/opt/…/copilot (deleted)` resolve to that pid; `/opt/copilot-evil (deleted)` refuses; a host whose command flips between raw and normalized between the two `inspectProcess` calls is impossible after AC1 (both normalized) — assert the incarnation check still fires on a real ppid/proc_start change. Add a unit test for the helper itself (Windows `\`-paths and `.exe` unchanged).
- AC4 Honest terminal diagnostic. The terminal `extension-unavailable` advice must not promise a retry. Required text shape: `[pij native] unavailable: extension-unavailable; native registration failed: <diagnostic>; no retry is scheduled — restart the Copilot CLI (/restart or relaunch) to recover; ordinary Copilot remains usable`. `registration-wait` keeps "retrying when available". The daemon-side refusal at registration.rs:384 names the observed executable basename and whether it was replaced, so the next such failure is diagnosable from the banner alone. Tests in `store.test.mjs` (reporter) and a Rust test on the refusal text. Diagnostics never include message bodies, keys or env (existing rule).
- AC4a (amendment, prime-approved 2026-09-09 at the coder's finding that `NativeError.message` can carry raw HTTP bodies): the banner projects only locally authored diagnostics or the daemon's structured host-refusal fields (basename, replaced), never raw `event.diagnostic`; unknown remote metadata projects the HTTP status only; unknown OS/SDK errors project `native initialization failed`. Shipped as `safeDiagnostic` in store.mjs.
- AC5 Docs: `docs/how/copilot-native-extension.md` gains an "In-place CLI upgrade" note: a replaced executable is accepted for same-session reattachment; `extensions_reload` never re-execs the host; what to do when the banner says restart. `docs/how/pij-rs-api.md` only if a refusal string it pins changes.
- AC6 Proof: the AC2 test RED on the pre-fix tree and GREEN after, run on Linux twice — locally in Docker (`docker run --rm --platform linux/arm64 -v "$PWD":/w -w /w rust:<pinned> ~/.cargo/bin/cargo test -p pij-daemon replaced_executable` — pin to the toolchain in `rust-toolchain.toml`; a cargo target dir inside the container, never the host's `target/`) and on CI's ubuntu `rust` job after push. Extension tests via `npm test` (node:test). Both outputs cited verbatim (tails) in report.md. A real `extensions_reload` on a Linux Copilot host is NOT available on this machine; say so in the report. The closing receipt on Jordan's Linux box is the prime's, not the coder's.

## Non-goals
Replaying messages or minting a replacement identity to hide the failure (issue forbids). The queued-message stall in github/copilot-cli#4705. Windows: Rust `is_copilot_host` only matches basename `copilot` (no `.exe`) — pre-existing, ledgered, not this plan. macOS ps path (`ucomm=`) never carries the suffix — no change. No legacy TS edits.
