**Mode**: Simple

**Spec**: [generic-sqlite-session-tool-spec.md](./generic-sqlite-session-tool-spec.md)
**Status**: COMPLETE

## Summary

Build `session-sql`, a pi extension that gives the current pi session a private SQLite workbench for structured agent state. The plan uses the existing L2 pij harness, scaffolds the extension through `npm run new -- session-sql`, keeps SQLite/storage behavior in a pi-free store, wires the model-facing `sql` tool plus human-facing `/sql` command, and proves behavior through store tests, deterministic smoke, self-check, and a manual resume proof. The implementation also bumps the runtime policy to Node `>=24`, supports native SQLite extension loading when exposed by Node, and documents how agents should use custom tables beyond the built-in todo schema.

### Acceptance Criteria

- [x] In a pi session, the agent can execute a generic SQL request against a private current-session store and receive structured success, row, mutation, or error results.
- [x] A human can run `/sql status` and see that the session SQL store is ready, which session it belongs to, which default tables are present, and whether native extension loading is available.
- [x] A human can run `/sql schema` and inspect the default schema without relying on model behavior.
- [x] A human can run `/sql <query>` to insert and select data, and query results are rendered compactly with stable success/error phrases suitable for smoke tests.
- [x] A human can reset the current session store and get a fresh store containing the default schema and no prior user rows.
- [x] A newly created session store includes a versioned default schema with session metadata, todos, and todo dependency support.
- [x] Agent-created custom tables and rows survive close/reopen of the same session store and are not removed by default schema initialization.
- [x] Data written in a session remains available after `/reload`, after process exit, and after later resume of the same session, as long as the underlying user pi state remains present.
- [x] A new session or forked session starts with its own empty store and does not inherit rows from the parent/source session.
- [x] The store artifacts are written outside the repository so normal project git status is not polluted by SQL usage.
- [x] Large result sets are capped at a 200-row returned preview, marked as truncated when applicable, and do not flood the model context or TUI.
- [x] Expected SQL and store errors are returned as tagged/structured failures and shown to humans as readable error messages.
- [x] Validation passes through type-checking, store tests, lint, deterministic `session-sql` smoke, self-check, and a recorded manual resume proof.
- [x] Native SQLite extension loading is available in v1 when supported by the runtime, so advanced local use cases such as vector search are not blocked by the session SQL wrapper.
