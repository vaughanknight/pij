### Executive Briefing
- **Purpose**: a `pij report now` card can be silently lost when a daemon descriptor write interleaves with it. The write LAW is not the gap — `statusPrev/Next/At/Seq/WrittenBy` are already contested fields owned by `cli` (`core/registry-write.ts:88-92`), so a daemon *merging* write restores disk's status. The remaining window is the registry's own read-modify-write: `FsRegistry.publish()` reads `existing` once, merges, then writes the file with no lock/CAS (`adapters/fs-registry.ts` — see Pre-Implementation Check). A CLI `writeExact` landing between that read and that write is overwritten by the daemon's merged copy (which carried the pre-CLI status from disk). The CLI side has the mirror window (`core/cli.ts:4089` `writeExact` after a re-read at `:4060`).
- **Hypothesis to PROVE FIRST (T001)**: reproduce with an interleaving seam, not by reading.
- **Goals**: ✅ AC-19 an interleaved write in either direction never drops the other side's fields · ✅ the fix lives in the write seam (adapter), not in callers · ✅ no `SessionDescriptor` schema change
- **Non-Goals**: ❌ changing field ownership · ❌ touching `writeExact` call sites' semantics beyond a read-back-and-reapply-once if needed · ❌ spine lock changes (item 15)
