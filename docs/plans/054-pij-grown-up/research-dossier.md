## The Ask

Jordan wants pij to graduate from a heuristic, prose-governed peer fabric into a deterministic platform: the governance spine machine-readable (JSON, filterable per peer), a new first-class **Project** entity (description, plan link, task lists, assigned prime), every running node in a proper parent graph rooted at primes (parentless boots get adopted in), per-node current-task plus a split between pij-owned `system_state` and orchestrator-set semantic state, richer node metadata (model, context max/current, harness, thinking level), and enough tmux identity to open any node in a terminal. A UI over this data is explicitly out of scope, but the data must be shaped for one. This dossier maps what exists today, what the ask actually changes, and which decisions the plan must resolve — feeding the human-directed workshop on data store/location/lookup/availability and DAG mechanics.

## Answer

1. The runtime substrate is already deterministic-friendly: one JSON descriptor per peer under `~/.pij/` with atomic writes and sha-keyed identity sidecars — no sqlite anywhere, and the one sqlite hypothesis (s053) was investigated and disproved.
2. Trees exist (plan 046, shipped) but as an orphan-tolerant projection over `parentId`/`spawnedBy`; the ask upgrades them to an enforced parent invariant (all non-primes parented, adoption drives orphans in), and 046's "no tree database" non-goal is explicitly up for reopening.
3. State today is a two-writer `working|idle` plus regex pane-scraping with a documented false-positive history; a richer self-report enum (`SessionState`) already exists but is unused by the ask's actors — the system_state/orchestrator-state split is a formalization, not an invention.
4. Governance is the outlier: the spine is a 336KB markdown event log, and the only JSON artifact (`prime-flow.json`) is legacy-format and CLI-disconnected (E309) — while the `harness flow` CLI (v0.12) already supports custom schema'd flow types with single-writer discipline, a candidate substrate for spine/projects.
5. Metadata is half-there: `boundModel` + `effort` are spawn pins and context-max is derivable by joining `boundModel` → `.pi/models.json` (`contextWindow`/`maxTokens`); context-current does not exist anywhere and per-harness feasibility is the weakest evidence in this dossier.
6. Terminal addressability is one field short: only `paneId` is stored, but the daemon already demonstrates deriving `window_id` from a pane via `tmux display-message` — capture-at-bind plus derive-on-read are both viable.
7. The graph work has a hard upstream dependency: s051 is mid-flight fixing the exact ownership corruption (issue #20: parent derived from cwd, not caller) that a trustworthy DAG requires, and s052 gates any product landing.
