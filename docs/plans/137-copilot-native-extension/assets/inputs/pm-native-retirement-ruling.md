# PM explicit retirement versus ordinary cold resume

2026-09-05. No new provenance field/schema.

- Automatic cold resume may nominate an existing address ONLY from currently native-attested Copilot provenance, including a dead-process row whose attestation survives. Daemon independently proves prior incarnation dead/replaced and new native host/pane; live/conflicting owners refuse.
- Explicit tombstone/supersedes clears attestation deliberately. Never infer prior native ownership from session/state alone, and never automatically resurrect that retired Pij address or inherit its old queue.
- Reopening a retired native conversation may attach as a FRESH Pij seat/address after current host validation, without retargeting predecessor mail. Fresh registration naming must not collide with an old tombstone (including A->B->A in one process). A newly minted PID-independent id for a new attachment is acceptable; id becomes stable once registered, and same-native attested cold-resume reuses it. Freeze the chosen registration id across retries. No migration scan of old PID-scoped journals.
- Valid Pij spawn/prebind correlation still takes precedence. Explicit retired launch intent is not silently repurposed. Legacy/unproven conflicting pane ownership still refuses; this rule is not a generic stale-record takeover mechanism.
- Daemon owns public HTTP/SQLite dead/live/new-native proof. Runtime owns actual chooseRegistration+realFS journal composition. PM owns final real CLI acceptance. Both owners may exchange read-only source/binary pointers, no private interface changes.
