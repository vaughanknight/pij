## FIX-1 (HIGH, F-001) — a recycled pane id is no longer proof of life

**The bug.** `classifyAttachment()` returned `live` on `paneLive` alone, and
`paneLive` came from a bare `#{pane_dead}` query. The reviewer reproduced the
reuse directly (private tmux server, kill, restart, `%0` → `%0`). Because
`planRevive()` refuses `live` *before* it considers `--print` or
`--assume-dead`, an unrelated `%N` in a post-reboot server could make a seat
permanently unrevivable — on exactly the path this feature exists for.

**The fix — corroborate the pane by identity, the same discipline already
applied to the pid axis.** `AttachmentProbe.paneLive: boolean` is replaced by
`pane: PaneObservation`:

| value | meaning | signal used |
|---|---|---|
| `ours` | the pane exists **and** its `#{pane_pid}` equals the pid this seat recorded | `#{pane_dead},#{pane_pid}` |
| `not-ours` | a pane with that id exists but runs something else | same query, pid mismatch |
| `gone` | tmux answered and there is no such pane | tmux exits **0 with an empty body** for an unknown pane |
| `unprobed` | tmux could not be asked at all | non-zero exit / `ENOENT` |

`#{pane_pid}` is the signal chosen because it is *the very field pij already
records as a seat's pid* at spawn and adopt time (`cli.ts` records
`#{pane_pid}`), so no new bookkeeping is needed for the comparison to be
meaningful.

New rule: **cannot corroborate ⇒ `uncertain`, never `live`.** `uncertain`
already gates writes and is already overridable with `--assume-dead`, so the
operator's escape hatch is restored on the reboot path.

**The forbidden direction is preserved.** A `not-ours` pane stops at `uncertain`
and deliberately does **not** fall through to the pid axis, where
`terminalObserved` or boot-time could otherwise return `stale`. A pane that
might be alive must never be called dead. Locked by the test *"a reused pane id
never classifies stale, so nothing here can call a live pane dead"* and by
mutation **G17**.

Verified end to end through the real CLI: a reused `%7` prints
`priorAttachment: "uncertain" / priorPane: "not-ours"`, a plain `pij revive`
is refused **naming the recycled identifier**, and `--assume-dead` still
revives it.

## FIX-6 (HIGH) — a recycled identifier corroborated by another recycled identifier

**What the reviewer observed.** `observePane()` decided a pane was `ours` on
equality of `#{pane_pid}` and the descriptor pid *and nothing else*. Pids restart
at the bottom of the range in a new kernel for exactly the reason pane ids
restart at `%0` in a new tmux server. On a fresh `%0` server, with a descriptor
whose recorded activity predated this host's boot but whose recorded pid equalled
the fresh pane's pid, the real CLI answered:

```text
E-ARG: session 'pij-reused' still has a live prior attachment; close it before reviving
```

Irrevocable: `planRevive` refuses `live` *before* `--print` or `--assume-dead` are
considered, so the operator's override could not rescue the reboot path.

**The principle, now encoded in the code at the ordering decision**
(`core/revive.ts`, above the `hostRebootInvalidates` call):

> A RECYCLED IDENTIFIER CAN NEVER BE CORROBORATED BY ANOTHER RECYCLED IDENTIFIER.
> ONLY MONOTONIC OR ABSOLUTE TIME EVIDENCE BREAKS THE TIE.

The rule the ordering encodes is stated there in one line: **no `live` return may
precede the time evidence.**

**What changed.**

1. **Ordering.** `hostRebootInvalidates(probe)` now runs *above* the `ours`
   branch. If the host booted after the descriptor's newest recorded activity,
   nothing of that seat survived — a boot destroys every process on the machine —
   so the verdict is `stale` whatever any identifier says.
   - `not-ours` deliberately stays *above* the time evidence. It is the one branch
     that can return neither `live` nor `stale`, so it cannot be a false
     corroboration, and leaving it there keeps the reviewed F-001 property
     (`not-ours` never falls through to `stale`) byte-for-byte intact.

4. **`PANE_START_SKEW_MS = 5_000`** — `ps` reports whole seconds and a descriptor

# Fix round 03 — FIX-7: the tolerance pointed the wrong way

Packet: `docs/plans/072-reboot-rehydrate/fix-packet-03.md`. Reviewer section:
`review-s072.md` § "Fix round 02 re-review". **One item.** Closed and not
re-opened: the host-reboot ordering, the `ps` fallback ladder, the `not-ours`
placement, F-002, F-003, and integrity questions A/B/C.

## The finding

`paneIdentityCorroborated` compared:

```ts
paneProcessStartedAtMs <= lastActivityAtMs + PANE_START_SKEW_MS   // 5_000
```

The tolerance was added to the *far* side, so a process that started up to five
seconds **after** our seat's newest recorded activity still read as ours, and
therefore as irrevocably `live`. The reviewer built it through the real CLI: a
fresh `%0` server whose pane process started at `03:30:25Z`, against a matching
post-boot descriptor last active at `03:30:21Z` — four seconds earlier — returned

```text
E-ARG: session 'pij-skew' still has a live prior attachment; close it before reviving
```

ahead of `--assume-dead`. My own `+4_000` test *required* that result, so it was
deliberate, not untested.

## The principle (encoded at the constant, `core/revive.ts`)

> A TOLERANCE MAY ONLY EVER WIDEN THE UNCERTAIN BAND, NEVER THE CONFIDENT ONE.
> Slack, skew and fuzz exist because MEASUREMENT IS IMPRECISE, and imprecision
> can only ever make you LESS sure of a verdict — never more.

Same family as the round-2 rule at the ordering site: that one says which
*evidence* may settle a tie, this one says which *direction* a tolerance may move
a verdict. The old constant converted a measurement limit into manufactured
certainty by extending `live` forward in time.

## What changed

1. **`PANE_START_SKEW_MS = 5_000` → `PANE_START_MIN_LEAD_MS = 1_000`**, and the
   comparison moved to the near side: `start <= lastActivity - MIN_LEAD`. The
   constant was **renamed** because its meaning inverted — it is no longer slack
   granted after our evidence, it is a lead **required before** it, and leaving
   "SKEW" on it would preserve the misreading that caused this.
2. **The boundary.** `ps -o lstart=` resolves whole seconds, so a process that
   started in the same second as the recorded activity is indistinguishable from
   one that started just after it. One full second of lead is therefore the
   smallest claim the signal can actually support. Exactly one second before ⇒
   `live`; same second ⇒ `uncertain`; later ⇒ `uncertain`.
3. **No-false-dead is intact.** Everything the tolerance no longer covers becomes
   `uncertain`, which `--assume-dead` overrides — an operator override, never a
   corpse. The concrete cost: a brand-new seat that has done nothing since it
   started reads `uncertain` for its first second.
4. **`uncertaintyReason`** reworded — it used to say the process "STARTED AFTER"
   our activity, which is now only one of the two ways to fail the test. It says
   "did not start before this seat's last recorded activity (ps lstart,
   whole-second resolution)". The integration assertion was updated with it.
5. **`pij-still-live` fixture made deterministic.** It anchored on
   `new Date()`, which only satisfies the new one-second lead if vitest happened
   to take a second to reach that line. It now anchors on this process's own
   start (`process.uptime()`), so the fixture's meaning — "activity recorded
   after the pane's process started" — no longer depends on run speed.
6. **Not built: durable incarnation identity.** The reviewer's second option and
   the right long-term answer; explicitly out of scope by the packet three rounds
   in. **Follow-up:** record a per-incarnation nonce at spawn and compare it
   instead of inferring identity from wall-clock times. That removes this whole
   class — pane id, pid, and start time all become corroboration for a signal
   that is not recycled by design.
