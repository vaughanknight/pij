# pij governance migration — dual-run posture and the cutover contract

Plan 054 stood up a machine-wide, schema-versioned JSON platform (projects,
assignments, the spine event log — see `docs/how/pij-platform.md`). This doc
is the migration contract for how that platform coexists with the prose
governance spine, and what it takes to switch. It states posture, not
procedure: **nothing in plan 054 executes a cutover** (hard stop R4).

## Dual-run posture (current, binding)

Two spines run side by side:

| Surface | File(s) | Writer | Role today |
|---|---|---|---|
| **Prose spine** | `government/spine.md` | o-prime / stream orchestrators (single-writer convention) | **AUTHORITATIVE.** Rulings, seat changes, pending decisions — the governance record of record. |
| **JSON spine** | `~/.pij/spine/events.ndjson` (+ `~/.pij/spine/spine.md`, regenerated by `pij spine render`) | any actor via `pij` verbs — every write an attributed append-only event | **Telemetry + platform truth.** Machine-filterable history (`pij spine events --peer/--project`), anomaly evidence, UI substrate. |

Rules of the road while both exist:

- The prose spine stays authoritative for governance meaning. A JSON spine
  event never overrides, closes, or supersedes a prose ruling.
- The JSON spine is still real: platform writes (project/task/state/link)
  land there as attributed events regardless of the prose spine. Dual-run
  means both are true at once, in different registers — not that the JSON
  side is a draft.
- `~/.pij/spine/spine.md` is a **render**, not a second log: regenerate it
  with `pij spine render`; never hand-edit it (byte-stable for an unchanged
  log by contract, AC-10).
- Nothing copies events between the two spines automatically. Any manual
  echo of a prose ruling into the JSON spine (`pij spine append`) is
  attributed to whoever ran it, like any other write.

## Cutover — an explicit human ruling, never a side effect

Switching authority from the prose spine to the JSON platform is a
**governance act, not a code change**. It happens only when a human (Jordan
or a delegate with the authority) issues an explicit ruling artifact; no
plan, agent, prime, or tool may infer a cutover from usage patterns, file
sizes, or the passage of time (R4).

A cutover ruling must be a committed artifact (prose spine entry plus a
standalone ruling doc) answering, at minimum:

```markdown
# Ruling: governance spine cutover

- **Ruled by**: <human name> · **Date**: <YYYY-MM-DD>
- **New authority**: <which surfaces the JSON platform now owns; which — if
  any — stay prose>
- **Prose spine disposition**: <frozen at seq/date? archived where? does it
  keep any live role?>
- **Backfill**: <is prior prose history migrated, summarized, or left in
  place as the historical record?>
- **Writer contract**: <which verbs/CLIs are the sanctioned writers post-
  cutover; what becomes forbidden>
- **Rollback condition**: <what observation would reverse this ruling>
```

Until such an artifact exists, the answer to "has the cutover happened?" is
**no**, categorically.

## `government/prime-flow.json` — frozen (E309), superseded only by ruling

`government/prime-flow.json` predates the `harness flow` CLI's provenance
contract; the CLI now **fails closed on it (E309)** and manual JSON editing
is forbidden repo-wide (the CLI is the only sanctioned writer). That wreck
is first-party evidence for this whole migration's core law: *JSON alone is
not determinism — a schema'd, single-writer CLI plus a migration story is.*

Posture, by ruling of this plan:

- The file is **frozen as-is**: byte-untouched by plan 054, not migrated,
  not deleted, not hand-repaired. It stays in place as the historical
  record of the pre-CLI era.
- Nothing may resume writing it: no hand edits (E309 exists precisely
  because hand-cranked JSON rots), no new tooling targeting the legacy
  format.
- What supersedes it is decided **at cutover time, by the cutover ruling**
  (WS-3's replace posture): the natural successor is the pij platform
  itself (projects + assignments + spine), with a fresh CLI-written
  `harness flow` overlay as the alternative if flow semantics are wanted.
  Until that ruling, nothing supersedes it — it is simply inert.

## Not in scope here

Executing a cutover, migrating prose history, repairing or deleting
`prime-flow.json`, or granting any agent authority to do the above. This
doc defines the contract those future acts must satisfy; it grants nothing.
